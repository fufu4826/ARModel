## โครงสร้างใหม่

| ข้อมูล | ที่จัดเก็บ |
| --- | --- |
| แหล่งเรียนรู้ โมเดล และความสัมพันธ์ระหว่างกัน | ตาราง `projects`, `models` ใน D1 |
| สไลด์และการตั้งค่าหน้าเว็บ | `slider_items`, `site_settings` ใน D1 |
| Username และแฮชรหัสผ่าน | `admin_accounts` ใน D1 |
| สถิติ การใช้งานผู้ดูแล และประวัติการเข้าสู่ระบบ | ตาราง `events` ใน D1 พร้อมดัชนีชนิดและเวลา |
| ไฟล์ GLB รูปภาพ เสียง และเสียงฉบับร่าง | R2 |

Flask ติดต่อ D1 ผ่าน Worker ที่ตรวจ token ฝั่งเซิร์ฟเวอร์ เบราว์เซอร์ผู้ใช้
ไม่ได้รับ token นี้ และหน้า Admin จะไม่แก้ไฟล์บน GitHub อีกต่อไป
JSON เดิมยังเก็บไว้สำหรับนำเข้าและตรวจเทียบ แต่ไม่ถูกอ่านเป็นข้อมูลใช้งานจริง
ข้อมูลเสริมบางชนิด เช่น รายการรูปและรายละเอียดเหตุการณ์ ใช้คอลัมน์ JSON
ภายใน SQL ตามลักษณะข้อมูล ไม่ใช่ไฟล์ JSON ที่เขียนทับทั้งฐานข้อมูล

## สิ่งที่ตรวจในเครื่อง

- สร้างตารางและดัชนีผ่าน Wrangler D1 migrations แบบ `--local`
- นำเข้า 41 โมเดล 10 แหล่งเรียนรู้ 31 การตั้งค่า และ 2 สไลด์
- ตรวจทุกฟิลด์เดิม รวมถึง ID, URL ของ R2, รูปประกอบ เสียง และค่าการหมุน/ขนาด
- บันทึกลายนิ้วมือ SHA-256 ของไฟล์ต้นฉบับ และไม่แก้/ลบไฟล์ต้นฉบับ
- สคริปต์นำเข้าปฏิเสธฐานข้อมูลที่ไม่ว่าง ป้องกันการนำเข้าทับข้อมูลใหม่
- ทดสอบเพิ่ม แก้ไข ลบ และอ่านหน้าสาธารณะผ่าน Flask กับ D1 จำลองจริง
- การทดสอบอัปโหลดใช้ R2 จำลอง ไม่ได้อัปโหลดไฟล์จริงไปคลาวด์
- ปฏิเสธการบันทึกจากฟอร์มที่เปิดก่อนข้อมูลเปลี่ยนด้วย HTTP 409
- Foreign key และ transaction ป้องกันความสัมพันธ์เสียหรือบันทึกค้างครึ่งรายการ
- เมื่อติดต่อ D1 ไม่ได้ จะตอบ 503 โดยไม่อ่าน JSON เก่ามาแทน
- ประวัติเข้าสู่ระบบขัดข้องจะไม่ปล่อยให้ข้ามการจำกัดจำนวนครั้ง

## การย้ายบัญชีและประวัติเดิม

ยังไม่ได้สร้างหรือเปลี่ยนบัญชีผู้ดูแลจริง บัญชีเดิมต้องถูกนำเข้าในขั้นตอนย้ายระบบ
เพราะ runtime ใหม่จะไม่อ่านรหัสผ่านจากไฟล์ config หรือ `ADMIN_PASSWORD` อีกต่อไป

`scripts/import_admin_to_d1.py` รองรับแฮชเดิมจากไฟล์ private config ที่ระบุ
หรือ `ADMIN_PASSWORD_HASH` ของ process สำหรับการนำเข้าเท่านั้น โดยไม่แสดงแฮช
ไม่เปลี่ยนรหัสผ่าน และไม่เขียนทับบัญชีที่มีอยู่แล้ว สคริปต์จำกัดปลายทางเป็น
localhost สำหรับรีวิวในขั้นนี้ รหัสผ่านแบบข้อความธรรมดาจะไม่ถูกนำเข้าอัตโนมัติ

`scripts/import_d1_events.py` รองรับไฟล์ประวัติ JSON ที่ส่งออกไว้แล้ว
แยกชนิด `analytics`, `audit`, `login` รองรับทั้งอาร์เรย์และหนึ่งเหตุการณ์ต่อไฟล์
ไม่เพิ่มฟิลด์ใน payload ที่มีลายเซ็น audit จึงรักษาการตรวจลายเซ็นเดิม
การนำเข้าซ้ำไฟล์เดิมไม่สร้างแถวซ้ำ และไม่ลบต้นฉบับ

ยังไม่ได้นำเข้าประวัติจาก R2 บน production เพราะยังไม่มีการอนุมัติให้ย้ายคลาวด์
ต้องเก็บ archive เดิมไว้จนตรวจจำนวน ช่วงเวลา และลายเซ็นหลังย้ายครบแล้ว
กุญแจ `AUDIT_LOG_SIGNING_KEY` หรือ secret ที่เคยใช้เซ็นต้องรักษาไว้เพื่ออ่านประวัติเดิม

ไฟล์อัปโหลดใหม่และไฟล์เสียงต้องใช้ R2 รวมถึงตอนเปิดเว็บรีวิวในเครื่อง
หากยังไม่ได้ตั้งค่า R2 จะไม่เขียนไฟล์ลงโฟลเดอร์ local แทน
ตัวเขียนไฟล์ local ที่เหลืออยู่ถูกจำกัดให้ใช้เฉพาะ unit tests ที่แยกข้อมูลชั่วคราว

## ก่อนเปลี่ยน Production

1. ให้ผู้ใช้ตรวจรับ branch นี้และอนุมัติการทำงานบนคลาวด์ก่อน
2. สำรองข้อมูลล่าสุดจากระบบจริง รวมข้อมูลที่เพิ่มหลังวันที่โคลนและประวัติ R2
3. สร้าง D1 สำหรับ staging และผูก Worker กับฐานข้อมูลนั้น ใช้ HTTPS และ secret จริง
4. ใช้ schema ที่ผ่านการทดสอบ นำเข้าข้อมูลล่าสุดและแฮชบัญชีเดิมในปลายทางที่ว่าง
5. ตรวจจำนวน ทุกฟิลด์ URL สื่อ บัญชีผู้ดูแล และประวัติเดิมอีกครั้ง
6. ทดสอบการอัปโหลด R2 จริง การเข้าสู่ระบบ สิทธิ์ CSRF และ AR บนมือถือจริง
7. กำหนดเวลาหยุดแก้ข้อมูลช่วงย้าย เพื่อนำเข้าครั้งสุดท้ายโดยไม่ตกหล่น
8. เตรียม D1 export/Time Travel และแผนย้อนกลับ แล้วจึงอนุมัติ merge/deploy แยกขั้นตอน

ไฟล์ `cloudflare/d1/wrangler.toml` ปัจจุบันเป็นค่าทดสอบ local มี database ID
เป็น placeholder และปิด workers.dev ไม่ใช่การตั้งค่า production พร้อมเผยแพร่
ไม่มีคำสั่ง deploy อัตโนมัติในชุดงานนี้

## ข้อจำกัดที่ต้องรับทราบ

- ยังไม่มีหลักฐานว่าฐานข้อมูล D1 บนคลาวด์หรือการเขียน R2 จริงทำงานผ่านระบบใหม่นี้
- Local SQLite adapter ใช้เพื่อ unit tests เท่านั้น หลักฐาน integration ใช้ Wrangler D1 จริงในเครื่อง
- UI เดิมยังส่งรายการทั้งชุดให้ repository การบันทึกมี transaction และ version guard
  แต่ยังไม่ใช่ระบบแก้ไขพร้อมกันแบบหลายบัญชีหรือการซิงก์แบบ realtime
- Worker จำกัด 500 statements ต่อ batch เพื่อจำกัดงานต่อคำขอ ต้องปรับเป็นการบันทึกรายแถว
  ก่อนขยาย catalog มากกว่าขอบเขตนี้
- แดชบอร์ดยังคงอ่านเหตุการณ์ล่าสุดไม่เกิน 10,000 รายการตามพฤติกรรมเดิม
  ก่อนใช้งานปริมาณสูงควรเปลี่ยนเป็น SQL aggregation แยกช่วงเวลา
- ไฟล์ต้นฉบับ ข้อมูลสื่อ และการแก้ UI จากงานก่อนหน้านี้ยังถูกเก็บไว้ครบ
